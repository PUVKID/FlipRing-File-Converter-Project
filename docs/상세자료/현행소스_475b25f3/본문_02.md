### LEVEL 2 · 새 배포와 실제 확인 범위

새 배포 확인은 소스 → 실행 파일 → 설치된 실행 파일 → 출력 문서 순서로 연결했습니다.

실행 파일 안의 앱 및 모듈 21개를 현재 소스에서 컴파일 한 코드와 대조했고, 실행 폴더 1,207개 파일은 설치된 1,207개 파일과 크기·해시가 일치했습니다.

설치 폴더에는 제거기 파일 2개가 추가됩니다.

전체 소스 ZIP의 948개 항목은 실행 폴더의 파일 수와 다른 집합입니다.

단독 실행 파일과 설치된 실행 파일에서 각각 고정 DOCX 한 개로 HWP·HWPX 두 결과를 만들었습니다.

결과를 다시 읽어 한글, 문단과 표의 순서, 3×3 셀, 굵기·기울임, PNG 바이트와 픽셀을 대조했습니다.

다시 읽는 도구는 저장에 쓰인 python-hwpx 계열이므로 다른 한글 프로그램의 화면 대조와 구별합니다.

사용자의 Shift 시험은 PNG와 HWP 및 원본 보존·중앙 취소를 확인했고, HWPX 직접 조작은 아직 확인 중입니다.

기존 51·163·86회귀와 35개 독립 검사의 이력은 보존합니다. 이번 새 배포 확인 때 그 전체 검사를 다시 실행한 것으로 합산하지 않습니다. 최종 폴더 교체와 새 파일의 GitHub 원격 일치는 아직 완료되지 않았습니다.

### LEVEL 3 · 프리셋과 실행 전 점검

먼저 검수용 원본 사본과 결과를 비교할 위치를 정합니다. `photo_jpg`에는 사진을, `scan_pdf`에는 한 영 스캔을 선택합니다. 프리셋 이름은 1~80 자이며 중복 이름과 제어 문자를 피합니다. 일반 변환에는 PDF 전용 options를 끼워 넣지 않습니다.

PDF 추출은 `1,3-5`처럼 1부터 시작하는 범위를 넣고 출력 쪽 수와 순서를 확인합니다.

회전은 90·180·270중 하나, DPI는 60~600, 품질은 20~95, OCR 배치는 3·6·11중 하나만 허용됩니다.

처음에는 기본 DPI 200·품질 80·PSM 3을 기록하고, 한 번에 한 항목을 바꾼 결과를 비교하면 차이 원인을 좁히기 쉽습니다. `images` 압축 결과는 파일 크기뿐 아니라 확대했을 때 글자와 그림도 확인합니다.

OCR 전에 선택한 `kor`·`eng`의 traineddata와 Tesseract 준비를 확인합니다.

PDF 결과는 검색·복사, TXT는 글자와 줄 순서, DOCX는 문단·표, XLSX는 셀 위치를 원본과 대조합니다.

성공 파일이 생겼어도 오 인식은 남을 수 있습니다.

설정 파일 읽기 오류가 있으면 저장 차단을 해제하려고 덮어쓰지 말고 원본 오류와 파일을 보존합니다.

이 절은 재현 절차이며 이번 문서 편집에서 검사를 실행했다는 기록이 아닙니다.

`PresetStore`는 UTF-8 JSON 배열을 읽습니다.

이름은 양 끝 공백 제거 후 1~80 자이고 제어 문자를 거부하며 대소문자를 무시한 중복 이름을 허용하지 않습니다.

허용 키는 `name`, `kind`, `format`, `options`이고 일반 변환 프리셋은 빈 options만 받습니다.

입력/출력 경로를 프리셋에 끼워 넣지 않습니다.

PDF 옵션은 `Request`의 기본 값을 합친 뒤 검사합니다.

회전 90/180/270, 품질 20~95, DPI 60~600, PSM 3/6/11, 압축 lossless/images, OCR 언어 kor+eng/kor/eng를 허용합니다.

페이지 문자열은 최대 10,000 자이고 1부터 시작하는 단일 번호·범위·쉼표 목록 형식을 검사합니다.

OCR 출력은 pdf/txt/docx/xlsx, 이미지 변환은 png/jpg로 제한합니다.

읽기 오류가 난 프리셋 파일은 `error`에 원문을 남기고 쓰기를 차단합니다. 정상 저장은 같은 폴더의 임시 파일에 UTF-8 JSON을 쓰고 flush/fsync 후 교체합니다. 기본 프리셋은 JPG 변환 `photo_jpg`와 한국어+영어 OCR PDF `scan_pdf`입니다.

`preflight(path, dst)`는 입력 존재 →지원 출력 →외부 도구 →입력 읽기 →여유 공간 →쓰기 가능 순서로 점검합니다.

입력 4 배 +64MiB는 보수적인 준비 공간 추정 값이며 최종 출력 크기가 아닙니다. `missing`, `unsupported`, `helper`, `space`, `write`, `input` 오류 코드를 `error`와 함께 반환하고 통과 때만 `ok=true`, `code=ready`가 됩니다.

OCR 종료 확인은 부모 프로세스만 끝났는지가 아니라 묶인 자식도 종료했는지를 포함합니다. 코드의 Job Object 사용과 실제 취소 시험 결과를 구분하고, 표 추정 결과를 원본과 대조하지 않은 채 보존 성공으로 판정하지 않습니다.

- [`_serialized_pdfium`](../../../%EC%86%8C%EC%8A%A4/pdf_tools.py#L29): PDF 도구와 미리보기가 같은 네이티브 런타임에 동시에 진입하지 않는다.

- [`page_indices`](../../../%EC%86%8C%EC%8A%A4/pdf_tools.py#L207): 1부터 시작하는 범위를 검증하고 사용자가 쓴 페이지 순서를 유지한다. 예를 들어 1,3-5는 첫 페이지와 3~5쪽을 고르는 표현이며 잘못된 범위를 확인해야 합니다.

### LEVEL 3 · workspace_ui.py

감시를 켤 실제 폴더와 별도 결과 폴더를 지정하고 없는 폴더·같은 폴더 조건이 거부되는지 확인합니다. 쓰기 중인 파일과 두 번 동일 서명이 관측된 파일을 구분하여 전달 시점을 검수합니다. 선택창 취소, 문서/텍스트 품질 목표 안내, 실제 단계 표시도 별도 항목으로 확인합니다.

### LEVEL 3 · 새 배포와 실제 확인 범위

새 파일을 사용할 때에는 아래 전문 보완 절의 실행 파일·설치 파일·소스 ZIP 크기와 SHA-256을 각각 확인합니다.

설치 실행은 14.25초에 종료 코드 0으로 끝났고, 설치 후 창 응답과 앱 잠금 확인도 통과했습니다.

파일을 선택하고 HWP 또는 HWPX를 목표로 고른 뒤 결과의 한 글·표·그림과 원본 보존을 함께 확인하세요.

알 수 없는 HWP 스트림, 외부 연결, 실행 코드를 포함하는 문서는 지원 오류가 날 수 있습니다.

고정 표본에서는 단독·설치 실행 파일 모두 두 형식을 만들었고, 각각 한 개의 고정 검사가 결과를 확인했습니다.

사용자 시험에서 확인된 파일은 PNG와 HWP입니다.

JPG와 PNG의 RGB가 같았고 HWP의 한글·3×3 표·서식·그림도 기대 값과 맞았습니다.

HWPX 사용자 응답만으로 물리 완료를 처리하지 않았으며 별도 확인을 기다립니다.

중앙 취소는 사용자 직접 확인 근거입니다.

자동 검사나 사용자 표본에 없는 입력은 별도로 열어 검수해야 합니다. 기존 회귀의 과거 통과를 이번에 전부 재실행한 것으로 읽지 마세요. 최종 납품 교체·원격 게시·전체 완료 검사는 아직 남아 있습니다.

## LEVEL 4 - Advanced · 구현 경계와 변경 영향

현행 소스의 비교 기준과 납품 기준은 분리해야 합니다. 1.9 공개 원문 비교와 현재 1.11 구현을 연결하더라도 실행 바이너리의 동일 소스 결합은 새 빌드·패키지 검사로 입증해야 합니다.

ROOT 기반 경로와 Windows 네이티브 호출은 각각 파일 위치·운영체제 자원 경계이며 문서 파서의 입력 검증과 대체 관계가 아닙니다.

HWP 제한 저장은 인식되지 않는 부품을 출력 전에 명시 거부하는 정책을 포함합니다. 라이브러리의 빈 손실 보고서가 전체 메타데이터 보존을 증명하지 않으므로 알려진 입력 범위와 명시 거부를 함께 다룹니다. 코어의 구현·검사 결과가 있어도 한컴·COM·별도 파서 호환성이나 새 설치본 물리 동작은 확인한 범위 밖입니다.

### LEVEL 4 · 프리셋과 실행 전 점검

프리셋의 허용 키와 `Request` 검증은 저장된 JSON을 실행 인자로 옮기는 경계입니다. 경로를 프리셋 스키마에서 제외하고 일반 변환 options를 비워 두어, 파일 선택과 작업 설정을 분리합니다. 기본 값을 합친 뒤 범위를 검증하므로 누락된 값과 금지된 값이 같은 상태가 되지 않습니다.

PDF 렌더링의 DPI는 `dpi / 72` 배율로 적용됩니다.

해상도를 올리면 래스터 처리량이 늘어나므로 품질 상한만 확인해서 자원 사용을 설명할 수 없습니다. `images` 압축은 페이지 크기와 DPI로 그림의 최대 변을 계산하고 품질 값으로 교체 그림을 인코딩합니다. `lossless` 경로와 달리 그림 데이터 자체가 바뀌는 절충입니다.

PSM은 OCR 프로세스로 전달되는 별도 인자이며 렌더링의 선명 도 문제와 배치 분석 문제를 혼동하지 않아야합니다.

준비 공간 `입력 크기 × 4 + 64 MiB`는 실행 전에 적용하는 추정치입니다.

실제 결과 크기 보증이나 공간 예약이 아니므로 준비 성공과 출력 게시 성공을 별도 상태로 유지합니다.

프리셋 저장은 임시 파일 기록·flush·fsync 후 교체하고, 읽기 실패는 쓰기 차단으로 연결합니다.

손상된 설정을 빈 기본값으로 조용히 덮어쓰지 않는 것이 이 저장 경계의 핵심입니다.

`PresetStore`는 UTF-8 JSON 배열을 읽습니다.

이름은 양 끝 공백 제거 후 1~80 자이고 제어 문자를 거부하며 대소문자를 무시한 중복 이름을 허용하지 않습니다.

허용 키는 `name`, `kind`, `format`, `options`이고 일반 변환 프리셋은 빈 options만 받습니다.

입력/출력 경로를 프리셋에 끼워 넣지 않습니다.

PDF 옵션은 `Request`의 기본 값을 합친 뒤 검사합니다.

회전 90/180/270, 품질 20~95, DPI 60~600, PSM 3/6/11, 압축 lossless/images, OCR 언어 kor+eng/kor/eng를 허용합니다.

페이지 문자열은 최대 10,000 자이고 1부터 시작하는 단일 번호·범위·쉼표 목록 형식을 검사합니다.

OCR 출력은 pdf/txt/docx/xlsx, 이미지 변환은 png/jpg로 제한합니다.

읽기 오류가 난 프리셋 파일은 `error`에 원문을 남기고 쓰기를 차단합니다. 정상 저장은 같은 폴더의 임시 파일에 UTF-8 JSON을 쓰고 flush/fsync 후 교체합니다. 기본 프리셋은 JPG 변환 `photo_jpg`와 한국어+영어 OCR PDF `scan_pdf`입니다.

`preflight(path, dst)`는 입력 존재 →지원 출력 →외부 도구 →입력 읽기 →여유 공간 →쓰기 가능 순서로 점검합니다.

입력 4 배 +64MiB는 보수적인 준비 공간 추정 값이며 최종 출력 크기가 아닙니다. `missing`, `unsupported`, `helper`, `space`, `write`, `input` 오류 코드를 `error`와 함께 반환하고 통과 때만 `ok=true`, `code=ready`가 됩니다.

### LEVEL 4 · app.py

app은 사용자 입력·도구 관측·작업 상태·결과 기록이 합류하는 경계입니다. render _tools가 재표시와 재탐색을 분리하므로 언어 변경이 외부 도구 검색을 임의로 반복하지 않게합니다. RELEASE _VERSION과 데이터/자동 시작 이름은 역사 원문에 결합하며 현재 제품 값을 추정하는 기준으로 쓰지 않습니다.

Windows 셸 메모리 수명과 입력 이벤트, 버튼 모션의 소유권, 페이지 입력 영역 고정은 표현 변경과 별도 보존해야 할 동작입니다. 기록 입력 경로가 사라진 경우와 사용자 취소는 오류/취소로 전달하고 오래된 표시만으로 작업 성공을 추정하지 않습니다.

- [`select_in_explorer`](../../../%EC%86%8C%EC%8A%A4/app.py#L77): 파일을 실행하지 않고 탐색기에서 해당 파일을 선택한다. 예를 들어 기록에서 결과를 두 번 눌러 파일이 있는 위치를 찾는 동작입니다.
- [`DialogTranslator`](../../../%EC%86%8C%EC%8A%A4/app.py#L144): 앱에서 사용하는 Qt 표준 대화상자의 짧은 문구만 현지화한다. 파일 선택창의 짧은 버튼 문구를 한국어로 읽더라도 선택한 파일 이름은 번역하지 않습니다.
- [`file_urls`](../../../%EC%86%8C%EC%8A%A4/app.py#L212): 드롭에 포함된 모든 항목이 존재하는 로컬 파일/폴더인지 확인한다. 없는 파일이나 웹 주소를 파일 드롭으로 처리하지 않아야 합니다.

### LEVEL 4 · workspace_core.py

작업 실행과 출력 게시는 다른 책임입니다. `_single`·`_combined`가 작업 폴더에서 만든 결과를 `_publish`가 배타적 생성 모드 `xb`로 최종 경로에 복사합니다.

이미 존재하는 경로는 번호 후보로 건너뛰고, 복사 도중 실패하면 해당 호출이 만든 미완료 파일만 삭제합니다.

이는 기존 파일을 교체하는 트랜잭션과 다르며, 앞 단계 게시 파일을 전체 롤백하지 않습니다.

`complete` 콜백이 게시 성공 뒤 active.outputs와 result.outputs를 갱신하므로, 최종 outputs는 전체 단계의 모든 산출물 누적 목록이 아닙니다.

단계별 목록은 steps에 남습니다.

취소 예외는 cancelled, 다른 예외는 failed로 바꾸고 constraints _met를 false로 설정합니다.

반면 유한 압축 후보를 모두 시도해도 용량을 넘으면 completed 상태에서 조건 미달을 표현합니다.

호출자는 status 한 필드만 보고 요구 충족으로 처리하면 안 됩니다.

`_size_candidate`는 요청 품질, 요청보다 20 낮춘 값, 하한 20의 중복 제거 후보를 비교하며 더 작은 결과만 best로 선택합니다.

후보가 실제로 작아지지 않으면 원 입력도 best로 남을 수 있습니다.

PDF와 지원 이미지 외의 형식에는 이 재인코딩 탐색을 계속하지 않습니다.

레시피 저장소는 잠금 안에서 기존 내용을 읽고 검증한 후 같은 폴더의 임시 파일을 fsync 하고 교체합니다.

손상 읽기와 정상 빈 저장소를 구분하는 것이 기존 레시피 보존의 경계입니다.

- [`validate_recipe`](../../../%EC%86%8C%EC%8A%A4/workspace_core.py#L148): 코드·셸·임의 필드를 허용하지 않는 버전 1 JSON 레시피를 정규화한다. 레시피는 허용된 작업 목록이며 임의 명령이나 코드를 실행하는 파일이 아닙니다.
- [`preview_names`](../../../%EC%86%8C%EC%8A%A4/workspace_core.py#L201): 규칙에 확장자를 붙여 미리 보여 주며 경로 탈출과 Windows 예약 이름을 거부한다. 잘못된 규칙·예약 이름·경로 문자는 거부하며 자동으로 고쳐 주지 않습니다.
- [`_publish`](../../../%EC%86%8C%EC%8A%A4/workspace_core.py#L224): 배타적 생성으로 충돌을 회피하고 현재 호출이 만든 미완료 파일만 정리한다. 정상 이름 충돌은 번호를 붙인 새 이름으로 피하며 원본과 기존 결과를 덮어쓰지 않습니다.

- [`RecipeStore`](../../../%EC%86%8C%EC%8A%A4/workspace_core.py#L266): 손상된 저장소는 보존하고 유효한 레시피만 원자 교체한다. 저장 파일이 손상됐다고 원래 자료를 몰래 없애지 않습니다.
